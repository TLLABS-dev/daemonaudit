# m1-review — Codex report, 2026-08-27

## Scope

Reviewed all Python files under `src/daemonaudit/` and `tests/` against the
`AGENTS.md` invariants, with focused checks for output redaction, false passes,
symlink containment, detector coverage, Darwin behavior, and CLI exit semantics.
Ran the existing test suite (`13 passed`) and synthetic `Finding`, regex, and
root-symlink probes.

## Findings

### 1. Terminal output can print a raw credential from an unsanitized check title  [severity: blocker]

- **Where:** `src/daemonaudit/report/terminal.py:64-65`
- **What:** `Finding.title`, `why`, `fix`, `verify_cmd`, evidence, and the displayed
  tail of `CheckResult.note` are scrubbed, but `CheckResult.title` is passed to Rich
  unchanged. `Target.framework`, `Target.home`, and `Target.version` at lines 31-32
  are also unsanitized. A synthetic report whose check title is
  `sk-proj-ABCD1234EFGH5678IJKL9012MNOP3456` prints that entire value, while
  `to_json()` removes it. Thus the safety net is not actually applied to all terminal
  output. Rich also treats plain strings as markup by default, so attacker-controlled
  path/version text can affect rendering.
- **Why it matters:** The invariant is end-to-end: a future check exception/title, a
  daemon version string, or a user-selected home containing credential-shaped data can
  leak to stdout even though individual finding fields look safe.
- **Suggested fix:** Render a fully scrubbed report boundary, or at minimum call
  `scrub()` on every dynamic string including check titles and all target fields, and
  construct `Text(scrub(value))` so Rich does not interpret markup. Add a test that
  injects a shaped fake secret independently into every string field of `Target`,
  `Finding`, and `CheckResult`, captures terminal output, and asserts it is absent.

### 2. ERROR and SKIP scans can say “No findings” and exit successfully  [severity: blocker]

- **Where:** `src/daemonaudit/model.py:163-167`; `src/daemonaudit/report/terminal.py:35-36`; `src/daemonaudit/registry.py:58-64`
- **What:** `ScanReport.exit_code()` considers findings only. A report containing one
  or more `error`/`skip` results and no findings returns 0, and terminal output opens
  with the prominent “No findings” panel. This is a false pass at the CLI/CI boundary
  even though the internal result status is honest.
- **Why it matters:** Cron and CI generally consume the exit status, not the checks
  table. An audit that could not run is indistinguishable from a clean audit.
- **Suggested fix:** Reserve a non-zero exit code for incomplete scans (for example 3
  for error and 4 for skip/incomplete, documenting precedence versus findings), and
  change the green panel to “No findings among completed checks” whenever any result is
  not `pass`. Add tests for clean, low/medium finding, high finding, skip-only,
  error-only, and mixed results.

### 3. File access and size failures silently become PASS  [severity: should-fix]

- **Where:** `src/daemonaudit/checks/secrets.py:25-31,55-58`; `src/daemonaudit/checks/perms.py:33-37,84-87,136-150,188-192`
- **What:** `scan_file()` returns the same empty list for “no secrets,” an oversized
  file, and any `OSError`. Every permission check similarly continues after
  `file_mode()` errors. If all candidates are unreadable, too large, deleted during a
  race, or unsupported, SEC-001/PERM-001/002/003 can return `[]` and become `pass`.
  Silently skipping one volatile file can be reasonable, but silently reporting a
  complete clean check is not. Catching `NotSupported` inside individual POSIX checks
  also defeats the registry's intended conversion to `skip`.
- **Why it matters:** An attacker can make precisely the sensitive file unreadable to
  the auditor, or a routine permission problem can produce a reassuring false pass.
- **Suggested fix:** Make scan/read results distinguish `clean`, `skipped with reason`,
  and hits. Accumulate coverage failures and expose an incomplete/error result (the
  current `list[Finding]` check API may need a narrow extension). Let platform-wide
  `NotSupported` propagate. At minimum, raise `Skipped` if no candidate was
  successfully inspected; ideally report partial coverage without discarding real
  findings. Oversize files must also be surfaced, not treated as clean.

### 4. A symlinked daemon-home root escapes containment; entry walking lacks the root guard  [severity: blocker]

- **Where:** `src/daemonaudit/discover/hermes.py:70-73`; `src/daemonaudit/checks/_walk.py:12-18,32-46`
- **What:** Discovery accepts a symlink supplied via `--home` because `is_dir()` follows
  it. `walk_files()` refuses a symlink root, but `walk_entries()` has no equivalent
  guard and traverses it: a local probe with `home -> outside/` yielded
  `home/secret`. More generally, `Path.is_symlink()` followed later by `stat()` or
  `read_bytes()` is a TOCTOU sequence; a path can be swapped after validation and the
  later operation follows it.
- **Why it matters:** PERM-003 can inspect and report paths outside the selected daemon
  home, and raceable reads in SEC-001 can cross the boundary despite the “never follow
  symlinks” invariant.
- **Suggested fix:** Reject a symlink daemon-home during discovery and give
  `walk_entries()` the same root checks as `walk_files()`. For robust hostile-tree
  handling, walk/open relative to directory file descriptors with no-follow semantics
  (`O_NOFOLLOW`, `dir_fd`, and post-open `fstat`) on POSIX; at least re-lstat immediately
  before access and verify the resolved parent remains under an anchored, non-symlink
  home. Add tests for a symlinked root, symlinked intermediate directory, and a swap
  between enumeration and read.

### 5. Checks contain Hermes layout and remediation knowledge directly  [severity: should-fix]

- **Where:** `src/daemonaudit/checks/_walk.py:9-12`; `src/daemonaudit/checks/secrets.py:15,22,34-48,103`; `src/daemonaudit/checks/perms.py:9-15,65-78`
- **What:** Checks import Hermes-specific path sets directly from the adapter, define
  transcript names locally, recognize backup names themselves, and hard-code
  `~/.hermes/.env` in remediation. This contradicts the invariant that layout knowledge
  lives only in `discover/hermes.py` and checks ask `Target` for paths.
- **Why it matters:** OpenClaw/generic MCP support will either duplicate checks or make
  generic checks accumulate framework conditionals; `--home` users already receive a
  potentially wrong remediation path.
- **Suggested fix:** Put typed/path-group metadata on `Target` (vault files, private
  files/directories, sprawl roots, exclusions, backup candidates, and preferred vault
  path). Keep naming/layout decisions in the adapter and have checks consume only that
  target-provided data. Build fix text from the actual target path.

### 6. Secret patterns miss common authorization forms and Slack app tokens, while generic matching is context-fragile  [severity: should-fix]

- **Where:** `src/daemonaudit/redact.py:31-59,76-83,101-124`; `tests/test_redact.py:5-20`
- **What:** Synthetic probes found no hit for `Authorization: Bearer <random token>` or
  a credential-shaped `xapp-...` Slack app token. There are no explicit patterns/tests
  for JWTs, Azure keys, Google OAuth client secrets, Discord webhook URLs, or other
  common provider forms. Some are caught only when assigned to a generic keyword (for
  example an Azure key or JWT after `TOKEN=`), so the same raw value in a header, JSON
  field not covered by the keyword list, or prose is missed. Conversely the generic
  rule treats long random base64/hex values assigned to any `*_TOKEN` as credentials;
  that may be appropriate for conservative scanning, but it will also flag non-secret
  session/CSRF/checksum data when variable names contain the broad `TOKEN`/`SECRET`
  suffix. The mixed-case/digit heuristic also rejects valid lowercase-only provider
  tokens unless they have at least four digits.
- **Why it matters:** The scanner currently leans toward false negatives after the
  known false-positive fixes, and output scrubbing inherits exactly the same coverage
  gaps as detection.
- **Suggested fix:** Add explicit structural patterns for supported provider token
  families and contextual patterns for bearer/JWT/URL credentials. Separate
  high-confidence redaction patterns from finding-classification patterns: output
  scrubbing should be broader than findings. Add positive and negative tables covering
  OpenRouter, Google API/OAuth, Discord bot/webhook, Azure, Slack bot/user/app tokens,
  JWT, bearer values, base64/hex config values, references, examples, and session-key
  names. C2 is the natural place to pin these evasions before changing detection.

### 7. Verification commands are GNU-specific and several shell snippets are unsafe or inaccurate  [severity: should-fix]

- **Where:** `src/daemonaudit/checks/perms.py:60,106-107,172-173,213-214,231-232,245-246`
- **What:** `stat -c` fails on Darwin (`stat -f '%Lp %N'` is the corresponding form).
  `chmod 600 '<dir>'/*` misses dotfiles and nested files and can fail on an empty
  directory. The executable-data `find` expression lacks parentheses, so `-type f` and
  `-perm -u+x` apply only to the `*.pid` branch; any `*.log` is printed regardless of
  executable state, and the command does not cover the other extensions the check
  inspects. Paths are interpolated between single quotes without escaping embedded
  quotes.
- **Why it matters:** `verify_cmd` is part of every finding's contract. On macOS these
  commands do not run, and on POSIX some can claim a fix is verified when it is not.
- **Suggested fix:** Put command construction/quoting behind the platform adapter
  (`shlex.quote`; Darwin-aware `stat`), or prefer invoking `daemonaudit scan` as the
  portable verifier. Correct `find` with grouped predicates and generate extensions
  from the same source as the check. Avoid glob-based recursive remediation.

### 8. CLI I/O failures bypass report handling, and JSON stdout still receives diagnostics on stderr without a documented contract  [severity: should-fix]

- **Where:** `src/daemonaudit/cli.py:21-45,55-76`
- **What:** Discovery, platform setup, report rendering, and JSON file writes are not
  caught. A bad output path produces argparse-independent Python traceback text and the
  interpreter's incidental exit code instead of a stable scanner error. Such traceback
  output is outside `scrub()`. The exit-code meanings are only in a model docstring and
  `--help` does not state them. `--json FILE` confirms on stderr, while `--json` emits
  JSON on stdout; this is workable but should be documented for automation.
- **Why it matters:** CI needs stable, documented outcomes and the redaction guarantee
  should include fatal paths, not only successfully constructed reports.
- **Suggested fix:** Add one top-level exception boundary that scrubs concise errors,
  returns a documented operational-error code, and emits tracebacks only under an
  explicit debug option after scrubbing. Document the exit-code matrix in CLI help and
  README, including the no-target and incomplete-scan cases.

## Things I checked that are fine

- `to_json()` serializes first and scrubs the complete JSON string; a synthetic shaped
  secret placed in every report string field was removed and the result remained valid
  JSON.
- Finding title/body/evidence/verify text and the displayed traceback tail are scrubbed
  in the terminal renderer.
- `RedactedSecret` has no raw-value field, and SEC-001 converts raw detector matches to
  redacted display/fingerprint objects before building findings.
- Ordinary symlinked files and directories inside a non-symlink fixture home are
  excluded by both walkers; the existing outside-file fixture confirms the common case.
- `PosixPlatform.file_mode()` correctly uses `os.lstat()` rather than `stat()`.
- `Platform.listening_sockets()` converts psutil access denial to `NotSupported`, which
  is the right Darwin behavior for a check to report SKIP rather than PASS. No M1 check
  invokes it yet.
- Registry-level unexpected exceptions become `error`, and explicit `Skipped` or
  platform `NotSupported` become `skip`; the false-pass issue arises where checks catch
  failures internally and in final exit/report semantics.
- Framework discovery is isolated in `discover/hermes.py`; the violation is checks
  importing its layout constants rather than consuming target-provided paths.
- No network client or outbound network operation exists in the reviewed M1 code.
- Existing fixtures contain visibly fake credential bodies and the suite passes.

## Open questions for Claude

- Should partial filesystem coverage become a fifth result status (`incomplete`), or
  should it be represented as `error` while retaining any findings already produced?
- Which stable exit-code precedence should apply when a scan has both HIGH findings and
  an errored/skipped check?
- Is a user-supplied symlink for `--home` intentionally supported? If so, it should be
  resolved once to an anchored root and reported as such; otherwise rejecting it is the
  simplest invariant-preserving behavior.
